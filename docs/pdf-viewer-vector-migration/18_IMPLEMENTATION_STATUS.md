# Implementation Status and Audit

**Last updated:** 2026-10-17 (M9: native rendering, no PDFium pixels in Auto or Vector mode) · 2026-09-26 (Direct2D backend and page host, blend modes, soft masks, tiling patterns, vertical writing, glyph clips, two-circle radials, predefined CJK CMaps, JPEG 2000, mesh shadings, CCITT, JBIG2, knockout and non-isolated groups, encryption, certificate encryption, permissions) · branch `feat/vector-migration-gaps` · PR ramanacr/pdf-viewer#1
**Scope of this document:** what the first implementation pass (commits `b0ab63c` … `2e2fdd7`, 2026-09-21) delivered against this bundle, what it got wrong, what the second pass fixed, and what remains — with evidence, not claims.

## 1. Audit of the first pass

### What it did well

- **The seams are right.** `PdfEngine.Vector` and `PdfEngine.Vector.Windows` exist, are in `PdfViewer.slnx`, and `PdfEngine.Vector` has no reference to `PdfEngine.Pdfium` (ADR-007). PDFium is referenced only by the test project, as an oracle.
- **Canonical IR exists.** An immutable `PdfDisplayList` with a typed command hierarchy, a stable `PdfFallbackReason` enum and a `PdfFallbackToken` carrying no PDFium types (04, 06).
- **Engine selection is centralized** in `PdfDocumentServiceFactory` with `PDF_ENGINE_MODE`, and the UI exposes Auto / Vector / PDFium plus a per-page engine badge.
- **Parser foundations:** lexer, parser, classic xref + xref streams + object streams, `/Prev` chains with cycle guard, page-tree inheritance, Flate/ASCIIHex/ASCII85/RunLength with predictors, a `PdfSecurityLimits` class, outline extraction.
- **Non-rendering features left on PDFium** as ADR-008 requires; existing viewer tests were kept green.

### What it got wrong (severity-ordered)

## 2. What the second pass changed

Every item below has tests in `tests/PdfEngine.Vector.Tests` or `tests/PdfViewer.Tests`.

### Core (`PdfEngine.Vector`)
- **Interpreter rewrite** (`Content/PdfContentInterpreter.cs`): Form XObjects (matrix, BBox clip, recursion + self-reference guard, transparency groups with correct alpha reset), Type3 fonts (glyph procedures executed, `d1` uncoloured), inline images (`BI/ID/EI`, abbreviations, exact-length and scan recovery), image XObjects, optional content (`/OCProperties /D`, `BDC /OC`, OCMD policies, XObject `/OC`), annotation normal appearances (12.5.5 algorithm, hidden/NoView flags), shading patterns and `sh` with function-sampled stops, text render modes (3/7 kept invisible for selection, 1/2/5/6 stroked, 4–7 classified), `TJ` as one run, `Tw`/`Tz` per spec, operand stack taken from the end, `BX/EX`.
- **Classified fallback everywhere** with conservative **page-space bounds**: soft masks, non-Normal blend modes, knockout groups, tiling patterns, pattern strokes, mesh/function shadings, unsupported colour spaces, JPX/JBIG2/CCITT, text clipping, resource limits, unknown operators (outside `BX/EX` only).
- **Budgets:** q-depth, operators, path segments, glyphs, image pixels (per image, per page), Type3 depth, wall-clock per page, cancellation every 256 operators — all produce typed `PdfResourceLimitException` → classified `ResourceLimit` fallback.
- **Typed errors** (`Diagnostics/PdfVectorExceptions.cs`): syntax, object resolution, unsupported feature, resource limit, encryption; every document-open data error surfaces as `PdfSyntaxException`.
- **Document:** encryption gate (`PdfEncryptedDocumentException`), xref reconstruction by scanning (damaged/missing `startxref`, xref-stream-only files, catalog in object streams), hybrid `/XRefStm`, object-header validation with one rebuild, object-count limit, cached object-stream index, serialized resolver, indirect `/Length`, off-thread single-flight display-list builds, **bounded LRU display-list cache** (`MaxCachedDisplayListCommands`), crop box clipped to media box, `/Rotate` snapped to 90°.
- **Images** (`Images/PdfImageSource.cs`): lazy decode (display lists don't pin pixels), any colour space, 1/2/4/8/16 bpc, `/Decode`, stencil masks with fill colour, `/SMask`, stencil and colour-key `/Mask`, JPEG passthrough with Adobe-CMYK handling.
- **JPEG 2000 reliability:** CoreJ2K 2.3 decoded lossy colour codestreams differently from run to run, so they went to the fallback renderer for a while. The root cause: its inverse wavelet transform rented the reconstruction buffers from the process-wide `ArrayPool` and did not clear them, and code-blocks with no coded passes (most chroma subbands of a lossy image) never write their area, which therefore kept whatever the pool last held. Clearing on return did not help, because other pool users return dirty buffers. CoreJ2K 2.4.1 clears the buffers on rent; the same codestream now decodes bit-identically, repeatedly and in parallel (tested with a deliberately dirtied pool). All JPEG 2000 images are drawn on the vector path again, decodes run on the calling thread and observe cancellation, and undecodable streams still fail as a typed `ImageDecode` region. Corpus: `ImageDecode` regions on the JPEG 2000 files 28 → 0 (GovDocs1 001307, 001658, 001659, 001967, 001977 and veraPDF 6-2-8-3-t03); page mean pixel diffs against PDFium 3.99–7.89 before (with those regions drawn by PDFium) and 5.00–7.66 after. Decode time on the largest corpus images is the same or lower than with 2.3 (1275×1650 CMYK 741 → 636 ms, 1026×1293 RGB 306 → 228 ms). The corpus "JPEG 2000 noise" in the edit and redraw smokes was this bug.
- **JPEG soft masks** (/SMask with /DCTDecode): the core has no JPEG codec, so it hands the mask to the backend (`PdfDecodedImage.JpegMask`), which decodes it with WIC or WPF and applies it as alpha. With the Symbol fix, no GovDocs file falls back to PDFium for fonts or images any more.
- **Streams, functions, colour** (merged from a parallel workstream): bounded streaming Flate, LZW with `/EarlyChange`, typed unknown-filter errors, image-filter stop (`DecodeImageStream`); PDF functions types 0/2/3/4 with bounds; CalGray/CalRGB/Lab/ICCBased (colour managed since the colour management work below; before it, via `/N` or `/Alternate`), Indexed over any base, Separation/DeviceN tint transforms, Pattern spaces, flagged unknowns.
- **Fonts** (merged from a parallel workstream): identity-keyed font cache, Standard/WinAnsi/MacRoman/Differences + AGL, token-based ToUnicode (arrays, surrogates, caps), real Standard-14 widths, code→CID CMaps (Identity, embedded, variable-length), CIDToGIDMap, sfnt `cmap` 0/4/6/12 lookup for embedded TrueType, Type3 model, descriptor metrics.

### Windows backend (`PdfEngine.Vector.Windows`)
- `WpfDisplayListCompiler` → frozen, resolution-independent `DrawingGroup`; `WindowsVectorRenderer` rasterizes it and **composites fallback regions last** from an `IPdfFallbackProvider` (hybrid) or outlines them (strict).
- **Glyph runs from the embedded TrueType/OpenType program by glyph ID** (ADR-006). Without a loadable program: a metric-compatible system substitute placed at the PDF-computed positions; if the substitute lacks a glyph, or the program is bare Type1/CFF, the run becomes a **backend fallback region** instead of `.notdef` boxes.
- **Fonts that are not embedded** are drawn with the installed font chosen by `SystemFontCatalog.Match`, the one routine editing, PDF/A conversion, annotations and both renderers share:
  1. the exact PostScript name, if its weight and slant fit;
  2. the family name as written, then without MT/PSMT/PS, then without the style words written into it (weight from Thin to Black, Italic/Oblique, Narrow/Condensed);
  3. aliases for PostScript and Adobe families (Helvetica to Arial, Palatino to Palatino Linotype, AvantGarde to Century Gothic, and so on), limited to the metric-compatible regular and bold weights;
  4. the class of font: fixed pitch, script, serif, else sans. A name that plainly says sans overrides a wrong serif flag.
  - A Symbol font re-encoded with codes of its own is drawn with the installed Symbol font by what each glyph is, and Adobe's private-use forms (the serif registered and copyright signs, pieces of tall brackets) by their standard characters (`Fonts/SymbolFontCodes`).
  - Over the 284 GovDocs files, 21 render closer to PDFium and 2 differ more: one is image noise, and one is Optima, which PDFium draws as a serif. Substitute glyphs are fitted to the document's /Widths in the Direct2D renderer, as Acrobat's substitutes are: a glyph wider than its width is narrowed so it does not run into the next, and a narrower one is widened by up to a tenth and centred in the rest. (PDFium leaves them as they are, so wide substitutes overlap there.)
- Correct image orientation, `/Rotate` + viewer rotation, shading extend bands and radial clip, hairline and dash handling in page units, byte-bounded image cache, one long-lived STA render thread, `AnalyzeAsync` and `BuildPageDrawingAsync` for hosts.

### Composition root (`PdfViewer`)
- (M9) The PDFium region provider is gone: no page, tile or region is drawn by PDFium in Auto or Vector mode (see "M9: native rendering" under the PDFium-free release gate).
- `HybridVectorDocumentService`: vector path honours `EnsureRenderDimensionsAllowed`; engine badge `Vector` / `Vector (N approximated)` / `Vector (N unsupported)` (strict) / `Unreadable page`; per-page `PdfEngineMetrics` (once per page, no document text) with `ToJsonReport()`; selection boxes from `TextToPage` normalized to the unrotated crop box (matches PDFium); lazy vector open after an engine switch.
- Showcase PDF and its test: a damaged JPEG the engine cannot decode is left out (PDFium leaves out what it cannot decode too), and everything else on the page, the knockout transparency group included, is drawn natively. (The showcase used a Multiply blend, then the knockout group, until each became native.)
- A race where a late text-extraction result overwrote already-populated segments is fixed (`PageViewModel`).

### Vector page host (E8) — decided: keep `Auto` default, build the host
- `WindowsVectorRenderer.BuildPageSurfaceAsync` builds a frozen `DrawingImage`: white page and vector content (regions the WPF renderer cannot draw show what it draws of them; strict mode outlines them), sized in points after `/Rotate` + viewer rotation.
- `IPdfDocumentService.GetVectorPageSurfaceAsync` (default: none). `HybridVectorDocumentService` returns a surface unless the page has more than 40 000 commands (live drawings re-render every frame; such pages are Direct2D bitmaps with detail tiles, as in the default host); surfaces are cached per page and rotation (LRU 24), cleared on open/close/engine switch.
- `PageViewModel.VectorSurface` / `PageSurface` / `HasSurface`: the page view binds `PageSurface`. A zoom change does not rebuild a surface and no page bitmap is held; very dense pages (native Direct2D bitmaps) and PDFium-mode pages (developer builds) stay on the bitmap path.
- **Night mode is live too:** the WPF surface is compiled with every paint, gradient stop and image colour-inverted on a black page (inversion commutes with source-over compositing; test: ≤ 1/255 mean difference). In the default Direct2D host the page bitmap and the detail tiles are drawn as by day and inverted on the GPU by a Direct2D Invert effect (M9).
- **Scroll cost:** `Views/PageSurfaceCache` gives a page image a `BitmapCache` at scale 1 while it fits 4096 device pixels, so scrolling composes a GPU texture and the vectors re-render only when the size changes (zoom). Larger (high-zoom) pages draw live.
- Tests: `VectorPageHostTests` (surface reuse across zoom, rotation, night surface = inverted day surface, bitmap path for PDFium/dense pages, hybrid region page stays live, hard edge at 16× zoom, cache rule). Smoke: the real viewer opened EngineShowcase and a path-heavy file on the live path, stayed responsive, badge `⚡ Vector`.

### Corpus and embedded font programs
- **Corpus:** `eng/vectorpdf/corpus/fetch-corpus.ps1` fetches the veraPDF corpus (CC BY 4.0) and the PDF Association PDF 2.0 examples (CC BY-SA 4.0) at pinned commits into a git-ignored cache and writes `manifest.json` (SHA-256, source, licence per file; 2 913 files). PDFs are never committed.
- **Corpus runner** reports the hybrid-beta gate inputs (`--summary`), per-detail fallback counts and worst pixel differences; `vectorpdf diffpage` writes vector | PDFium | difference images and dumps commands, content and per-font load status.
- **Font programs (`Fonts/Programs/`):** every embedded kind is normalized into an sfnt the backend loads — TrueType subsets get `name`/`OS/2`/`post`/`cmap` (and `hhea`/`hmtx` when inconsistent); bare CFF (Type1C, CIDFontType0C) is wrapped in OpenType; Type 1 (`FontFile`) is converted to CFF (eexec/charstring decryption, subrs inlined, flex, hint replacement, seac, FontMatrix baked into outlines). Glyph indices come from the CFF charset / built-in encoding / sfnt cmap per kind. Any invertible CFF FontMatrix is drawn: a Top DICT matrix that is not a uniform 1/unitsPerEm scale (narrow, skewed, rotated, mirrored, 1/2048 rounded) is rewritten in place to the standard scale and the rest becomes the face's glyph matrix (when the entry is too short to hold a standard scale, the program keeps its matrix, which DirectWrite applies). CID-keyed fonts whose FDArray Font DICTs carry a FontMatrix keep their program as it is: DirectWrite concatenates FD × Top as FreeType does (the FD matrix alone when the Top DICT has none), which one glyph matrix per face could not express for several FDs; the em in `head` follows the first glyph's FD × Top. Only a singular matrix is refused. Glyph advances stay on /W, /DW and /Widths in 1/1000 text space whatever the matrix; a simple font with an embedded Type1C or Type 1 (`FontFile`) program, no /Widths and a non-standard-14 name advances by the program's own widths (CFF charstring widths; Type 1 hsbw/sbw, a seac composite keeping its own) mapped through its FontMatrix and chosen through the font's encoding, as PDFium does. Codes past a /Widths array that is too short get /MissingWidth, else 0, as in PDFium. Drawing, text extraction and selection, and the editing encoder all read these advances through `PdfFont.GetGlyphWidth`. A program the backend still rejects becomes a classified fallback region — never a silent substitute.
- **Root cause found in the first pass's renderer:** WPF's font cache throws for a second font file loaded from a folder it has already read, and for a folder that is deleted and recreated. All embedded fonts were written to one folder, so **only the first embedded font per process ever rendered with its own glyphs**; the rest silently used system substitutes. Fonts now get one folder each under a per-renderer root.
- **Page boxes:** only an explicitly specified `/CropBox` is inherited, and it is clipped to the media box at the leaf (two corpus files rendered at the wrong size).

### Direct2D / DirectWrite backend (ADR-005; ADR-011 decided)
- `PdfEngine.Vector.Direct2D` (Vortice.Windows 3.8.3, MIT): D3D11 device (hardware, WARP fallback), Direct2D 1.1 device context, DirectWrite fonts from memory (custom font-file loader, no temp files), WIC JPEG decode. Clips are geometric-mask layers; hairlines use `StrokeTransformType.Hairline`; output larger than 2 048 px is tiled, and geometry realizations are shared across tiles; device loss recreates the device without reparsing (`SimulateDeviceLoss` test).
- **Default page host:** the page bitmap comes from Direct2D, and when the page is zoomed past that bitmap a **viewport detail tile** (visible area plus a margin, ≤ 4 096 px a side) is rendered at exact device resolution and laid over it; scrolling inside the margin reuses the tile. Zoom range 25–1 600 %. `PDF_VECTOR_HOST=wpf` selects the earlier WPF drawing host; the WPF renderer also stands in when no Direct3D device exists.
- **Host tuning (`vectorpdf tiles`, `eng/vectorpdf/baseline-tiles.txt`):** rectangular clips (`re W n`) are axis-aligned clips instead of offscreen layers, and other clip layers are bounded to their mask (a 58-command text page with 13 nested clips: 516 → 44 ms at 300 dpi). GPU tiles are 4 096 px (one replay per viewport tile instead of four). Replayers, with their tessellations, are cached per page and scale (day and night share them since M9), so scrolling at a fixed zoom reuses them (path-heavy fixture at 1 600 %: next tile 136 ms, versus 1.2 s before). The detail tile shows the visible area first, then the margin tile replaces it. `forceSoftware` measures the WARP tier (RDP, VMs).
- **Zero-copy detail tiles:** on a hardware tier in a local session, a detail tile is rendered into a shared Direct3D 11 texture and shown by a WPF `D3DImage` through a Direct3D 9Ex surface (`D3D9ExInterop`, four COM calls, no extra package): the pixels never leave the GPU. Next tile on light corpus pages p50 ≈ 30–40 ms against 130–175 ms for readback plus WPF bitmap (before WPF's upload). Software tier, RDP and `PDF_GPU_PRESENT=0` keep bitmaps; a lost display device drops the tile and the page bitmap shows until the next one.
- In developer builds, PDFium-mode pages get the same detail tiles (`RenderPageRegion`: FPDF_RenderPageBitmap with a negative origin). No other page or region is drawn by PDFium (M9).

### Portable Skia backend (web and Android, step 1)
- `PdfEngine.Vector.Skia` (net9.0, SkiaSharp 3.116.1, MIT) replays the display list on Skia's CPU raster canvas with the Direct2D backend's semantics: every command type, the 16 blend modes, soft masks, non-isolated and knockout groups, tiling patterns, mesh and function shadings, night mode and fallback regions. It is not used by the WPF app. Design, coverage, gaps and measurements: `src/PdfEngine.Vector.Skia/README.md`.
- `tests/PdfEngine.Vector.Skia.Tests` renders each fixture with Skia and Direct2D: 211 of 219 renders differ by a mean of at most 1.0 (0–255). A 200-page corpus sample at 96 dpi: mean per page 0.26 on average, median 0.01. Gaps: four-component JPEG data is classified for fallback (SkiaSharp decodes it as black), and small text is lighter than Direct2D's.
- Text in a font that is not embedded is shaped when it is drawn with a substitute (the web demo's Noto faces, or installed fonts): Arabic joining forms, lam-alef and other ligatures, GPOS marks, Indic pre-base vowel signs, reph and conjuncts, with the editing shaper (`TextShaper`, `IndicShaper`) and the substitute's GSUB and GPOS; no HarfBuzz. Arabic is taken as seen (left to right) and put back in reading order once; a word whose glyphs go right to left is read as it is. A pre-base vowel sign written before its consonant is moved after it before shaping. Each shaped word is fitted to the space its `/Widths` give it (narrowed, or widened by up to a tenth and centred). Embedded fonts and Latin text are drawn as before. The Skia, Direct2D and WPF backends share this code (`Text/SubstituteShaper`): each reads the substitute's font file once (`SkiaResources`, `D2DResources` and `WpfFontCache.GetShapingFont`) and draws the shaped glyphs, so the desktop app and the web demo shape alike; a word the substitute cannot shape (a glyph missing) is drawn glyph by glyph as before. The WPF backend, used only without a Direct3D device, draws a fitted word under its horizontal scale as Direct2D does. Shaping changes drawing only: the text page, selection and search read the characters. The shaper now keeps a glyph that a substitution split off (Noto Sans Arabic's dots) with its letter when right-to-left text is reversed; before, the dots of a word's first letter landed to its left, in the web demo and in text added with such a font. Tests: `SubstituteShapingTests` (Skia, 15: Segoe UI, Arial and Nirmala UI stand in for Noto; one more with the real Noto files when `NOTO_FONTS_DIR` is set) and `ShapingTests.ArabicGlyphsSplitOff_StayWithTheirLetter_WhenReversed` (engine, Noto only); `Direct2DSubstituteShapingTests` (engine, 14: the same cases by glyph id in the Direct2D backend, the fitted width, a font without the glyphs, the text page, the WPF backend against Direct2D by pixels, mean 0.1 to 0.3, and a word narrowed to its `/Widths` as wide in WPF as in Direct2D, within 1 px at 72 pt); `SubstituteShapingParityTests` (Skia, 2: a shaped Arabic and a shaped Devanagari page against Direct2D, mean channel difference 0.1 to 0.35).
- Characters a substitute lacks, on the desktop too: when no face of the Direct2D backend's substitute chain has every character of a run (Hebrew and Devanagari under Arial, Devanagari and Han), the face with most of them draws its own and each other character comes from an installed face that has it (`D2DResources.GetCharacterFace`), as the Skia backend's per-character faces draw it in the web demo. The face is chosen by script first (`Fonts/CharacterFaces`: Segoe UI or Arial for Arabic and Hebrew, Nirmala UI for Indic, Segoe UI Symbol or Segoe UI Emoji for symbols, and for Han Microsoft YaHei, Microsoft JhengHei, Yu Gothic or Malgun Gothic by the font's CID ordering, else by kana or hangul in the text or the font's name: the rule the web demo's `BundledFontIndex` now shares), then by DirectWrite's system font fallback (`IDWriteFactory2.SystemFontFallback`, with the language's locale for CJK). Each face's words are shaped with its own tables (`SubstituteShaper`, the words of that face only). Before, the characters the substitute lacked were left out. A run one face has whole is drawn as before (one face), and so are embedded fonts; text extraction, selection and search are unchanged. A run drawn from several faces is printed without its text description (the parts hold its glyphs out of order). `D2DResources.GetShapingFont` now also reads a face held in memory, through its loader's `IDWriteFontFileStream`; installed faces are still read from disk. Gaps: the WPF backend (no Direct3D device only) draws a run with one substitute and has no fallback chain, so it still leaves such characters out; a run one face of the chain has whole still takes that face, so all-Han text under a Japan1 font is drawn in Microsoft YaHei, the first CJK face of the chain, as before. Tests: `Direct2DCharacterFallbackTests` (engine, 10: the Hebrew and Devanagari run by face and glyph id, with the pre-base i sign and the ksha conjunct; its ink; Han by Japan1, GB1 and Korea1 ordering; Han ink; runs one face has; the system fallback for Ethiopic and Cherokee; a face in memory; the text page), and `SubstituteShapingParityTests.MixedRun_TakesCharactersTheSubstituteLacksFromTheSameFaces` (Skia with installed faces named by the same rule against Direct2D: mean 0.46 at 72 dpi, 0.20 at 144 dpi, no pixel off by more than 64).

### Transparency and patterns (M7)
- **IR:** `BeginCompositingGroup(bounds, alpha, blend, softMask, isolated, knockout)` / `EndCompositingGroup`, `PdfSoftMask` (luminosity or alpha, the mask group as its own display list, backdrop colour, sampled `/TR`), `DrawTilingPattern` + `PdfTilingPattern` (one cell as its own display list), `PushStrokeClip` (pattern-painted strokes).
- **Interpreter:** an object painted under a non-Normal blend mode or a soft mask is wrapped in a group of its own (the specified single-object result); transparency-group XObjects painted with a blend mode or soft mask become one compositing group; the soft-mask group is recorded when the ExtGState is set, with the CTM of that moment (cached per mask and CTM, depth-limited). Tiling cells are recorded once in pattern space (cached per pattern and, for uncoloured patterns, per colour; self-reference and depth are guarded); uncoloured patterns take their colour from `scn`. A mask or cell that itself needs fallback keeps the whole object on the fallback path.
- **Direct2D:** a group renders into an offscreen bitmap on its own device context; soft masks are rendered over their backdrop colour, turned into alpha with a luminosity colour matrix and `/TR` via a table transfer, and applied with an alpha-mask effect; blend modes use the Blend effect against a backdrop copied from the surface after its layers are popped (enclosing clips are re-applied to the group content), written back with a clipped source-copy. Opacity groups that contain a blend group are composited offscreen as a whole. Night mode draws the tile in true colours and inverts it with a Direct2D Invert effect (M9), because blend modes do not commute with inverting each paint. Tiling patterns rasterize one period at device resolution (every overlapping tile contributes) and fill with a wrapping bitmap brush, so the period is exact at any zoom.
- **WPF backend:** compositing groups, tiling patterns, glyph-outline clips and two-circle radials are classified as backend regions — WPF has no blend modes. Since M9 they show what the WPF renderer draws of them (no PDFium pixels); the WPF renderer only stands in where no Direct3D device exists.
- **Knockout groups (exact):** each element is composited as G·(1 − f) + E − C0·(1 − f), where E is the element rendered with the current clips over C0, the initial backdrop of a non-isolated group (over nothing in an isolated group), f its shape from a shape-mode render (every paint opaque, images as their parallelogram, pattern fills as their area). An element with a blend mode therefore blends with the initial backdrop, as 11.4.6.2 specifies, and a non-isolated group inside sees it as its backdrop. Knockouts of opaque, Normal-blend elements are downgraded to ordinary groups. A knockout group with more than 256 elements (each costs two offscreen renders of the group) is drawn as an ordinary group (M9; before, a `TransparencyGroup` fallback region).
- **Non-isolated groups (exact, at any depth):** a group whose content blends (or knocks out) starts from a copy of the backdrop, and the backdrop is removed again before the group's alpha, soft mask and blend mode apply: C = Cn + (Cn − C0)·(α0/αg − α0) (11.4.8), which premultiplied is R = Cn − C0·(1 − αg) for any backdrop alpha α0 (αg from an isolated render of the same content). The backdrop is whatever lies under the group: the page, or the partly transparent content of an enclosing isolated group, knockout element or soft-mask group. An opacity group that contains such a group is composited offscreen, so the inner group sees the enclosing group's pixels rather than the page under an opacity layer. PDFium composites non-isolated groups as isolated and ignores knockout, so these are verified against hand-computed values from 11.4 (`CompositingTests`, `TransparencyGroupTests`); where the features make no difference the renders agree with PDFium.
- **Glyph-outline clips:** text rendering modes 4–7 and pattern-filled text become `PushTextClip`; Direct2D unions the DirectWrite outlines of the runs into a layer mask. Type 3 glyphs add nothing to the clip and modes 3/7 draw nothing, as ISO 32000-2 9.3.6 specifies (PDFium agrees).
- **Radial shadings between arbitrary circles** (and holed concentric ones): Direct2D evaluates the largest t per pixel (sampled at pixel centres; PDFium samples at pixel corners, a half-pixel phase difference of ≤ 3/255).
- **Mesh and function shadings:** types 4–7 are decoded by `PdfMeshDecoder` (bit widths, `/Decode`, shared-edge flags, Coons interior points) and rasterized by Direct2D as Gouraud triangles, with patches subdivided at device resolution in the specified fold order; parametric meshes interpolate t and then map it through the function. Type 1 shadings sample f(x, y) at device pixels. Gradient stops are sampled at 257 points.
- Still classified: nothing in these areas for valid files.

### Bilevel image codecs
- **CCITTFaxDecode:** T.4 Modified Huffman (K = 0), mixed MR (K > 0) and T.6 MMR (K < 0) with EOL/RTC/EOFB, `/EncodedByteAlign`, `/BlackIs1`, `/Rows` and damaged-row recovery; bit-exact on Windows-encoded G3/G4 streams and a hand-coded MR stream.
- **JBIG2Decode:** MQ arithmetic decoder, IAx/IAID, the standard Huffman tables B.1–B.15 (canonical codes checked against Annex B) and custom tables; generic regions (templates 0–3, TPGDON, AT, MMR, unknown length), refinement regions (TPGRON), symbol dictionaries (arithmetic, Huffman, refinement/aggregation, context reuse), text regions (all corners, transposition, strips, refinement, symbol-ID run codes), pattern dictionaries, halftone regions and `/JBIG2Globals`. A test-side T.88 encoder produces streams that PDFium must decode identically (all cases bit-exact).
- **JPEG:** bytes before the SOI marker are skipped, as libjpeg does.
- **Text extraction:** CJK fonts without `/ToUnicode` map CIDs of the Adobe collections to Unicode through the inverted `Uni*-UTF16-H` CMaps.

### Predefined CJK CMaps and JPEG 2000
- **CMaps:** the 59 predefined CMaps of ISO 32000-2 Table 116 come from Adobe cmap-resources (BSD-3-Clause) at a pinned commit, fetched by `eng/vectorpdf/cmaps/build-cmaps.ps1` (SHA-256 per file in `cmaps-manifest.json`) and embedded deflated (843 KB). Named encodings and `usecmap` chains resolve through `PredefinedCMaps`; only names outside Table 116 (e.g. a collection name such as `Adobe-Korea1-2`, which veraPDF uses in its "fail" files) are still classified.
- **JPEG 2000:** `JPXDecode` images decode in the core with CoreJ2K 2.4.1 (managed, BSD-3-Clause), lossless and lossy alike: codestream dimensions and bit depths win, `/ColorSpace` is optional (component count selects Gray/RGB/CMYK), `/SMaskInData` takes opacity from the extra channel, `/Decode` is ignored. The SIZ marker is checked against the pixel limits before the decoder allocates; decoder failures are classified `ImageDecode` (200-mutation fuzz test).

### Colour management
- **ICC profiles** (`Color/IccProfile.cs`, `Color/ColorTransform.cs`): a managed reader for ICC v2 and v4 profiles, with no native code or new packages. It reads the header and tag table, gray TRC (`kTRC`), RGB matrix/TRC (`rXYZ`/`gXYZ`/`bXYZ` with `curv` or `para` curves), and `A2B0`..`A2B2` pipelines of type lut8 (`mft1`), lut16 (`mft2`) and lutAtoB (`mAB `: A curves, CLUT, M curves, matrix, B curves), for 1 to 8 input channels into a Lab or XYZ PCS. PCS colours go to sRGB with Bradford D50 to D65 adaptation. CLUTs interpolate as lcms2 does (tetrahedral over the last three inputs, linear over the others), so results match PDFium's lcms2.
  - The intent picks the A2B tag (absolute colorimetric uses A2B1; a missing tag falls back to another). ICCBased spaces use perceptual unless the content sets `/RI`, the `ri` operator or an image `/Intent`, because PDFium uses perceptual whatever the content says.
  - Parsing is defensive: profiles over 32 MB, more than 1024 tags, CLUTs over 4 M values, curves over 64 K entries, and any read outside a tag are rejected. A missing, broken or wrong-sized profile falls back to `/Alternate` or the device space for `/N` (mutation test with 3 000 profiles). A profile equivalent to sRGB (within one level on a 5-point cube) passes DeviceRGB values through unchanged.
  - Profiles are parsed once per stream, and shared by content hash across documents (64 entries).
- **DeviceCMYK** goes through a CMYK conversion instead of `(1 - c)(1 - k)`, with relative colorimetric by default, as Acrobat shows it. The conversion is Adobe's own U.S. Web Coated (SWOP) profile when an Adobe application installed it, else a built-in model (`Color/SwopApproximation.cs`): a Yule-Nielsen modified Neugebauer model with dot gain, fitted to PDFium's Adobe-like conversion (2.4 levels mean error on a 9-point grid). K 100 % is 33/30/30 (Acrobat 35/31/32), cyan 0/176/239 (Acrobat 0/174/239). `SwopApproximationFit` (skipped test) refits it.
  - The Windows RSWOP.icm profile is read correctly (within 3 levels of Windows' own colour system) but is not used for display. It is a different characterization: cyan is 0/159/215, it is 12.7 levels from PDFium on the grid, and on the corpus it was slightly further from PDFium than the built-in model (mean 0.7491 against 0.7461). The PDF/A converter still embeds it as the CMYK output intent (shared helper `SystemColorProfiles`).
- **Default colour spaces:** `/DefaultGray`, `/DefaultRGB` and `/DefaultCMYK` replace the device spaces for `cs`/`CS`, the `g`/`rg`/`k` operators, images and shadings (ISO 32000-2 8.6.5.6), but not inside a default space or an ICC `/Alternate`. PDFium ignores them for the operators, so a few veraPDF files with a `/DefaultCMYK` profile now differ from PDFium by up to 0.8/255 while matching the specification and Acrobat.
- **Images:** CMYK and colour-managed ICC images convert through a sampled grid (33-point cube for 3 channels, 17-point CMY cubes along K for 4, in linear light, then the sRGB curve); large images split across threads. The grid is within 2 levels of the exact conversion. CMYK JPEGs (Adobe-inverted or with `/Decode`) are now mapped by the core for both backends, so WPF and Direct2D give identical pixels (`PdfColorConversion` covers the backends' own CMYK path). A 3-megapixel CMYK JPEG decodes in 66 ms against 76 ms with the naive formula (Release). Word export still embeds such JPEGs as they are (`JpegIsSelfContained`).
- Separation and DeviceN alternates, Indexed bases, shadings and soft-mask backdrops convert through the same spaces, so a Separation into DeviceCMYK gets the managed CMYK. Blending is unchanged (in RGB after conversion).
- Not yet: the PDF/A output intent is not used as the CMYK default; blending in a CMYK group colour space; absolute colorimetric media-white scaling; ICC spaces with Lab or XYZ data; black point compensation.

### Encryption (Standard and public-key security handlers)
- `PdfStandardSecurityHandler` (ISO 32000-2 7.6.4): revisions 2–4 (RC4 40–128 bit; crypt filters `V2`/`AESV2` with `/StmF`, `/StrF` and per-stream `/Crypt` filters) and 5–6 (AES-256, `AESV3`, Algorithm 2.B hashing, SASLprep via NFKC). User and owner passwords (Algorithms 2, 4–7, 2.A); the empty user password opens owner-only protected files without a prompt.
- The resolver decrypts each object read from the file (strings recursively, stream data once) with its object key (Algorithm 1); objects inside object streams are covered by their stream; cross-reference streams, the `/Encrypt` dictionary and — with `/EncryptMetadata false` — metadata streams stay plain. A missing or wrong password is a typed `PdfEncryptedDocumentException { PasswordRequired }`.
- `PdfSecurityHandler` is the shared base (crypt filters, Algorithm 1 object keys, RC4, AES-CBC); `PdfSecurityHandler.Create` dispatches `/Standard` and `/Adobe.PubSec`.
- **Certificate (public-key) encryption** — which PDFium cannot open at all — is handled by `PdfPublicKeySecurityHandler` (ISO 32000-2 7.6.5): sub-filters `adbe.pkcs7.s3`, `s4` and `s5` (recipients in `/Recipients` or in the crypt filter). `CmsEnvelopedData` decrypts each PKCS#7 envelope with in-box .NET only: key transport RSA PKCS#1 v1.5 or OAEP (hash from the parameters), recipient by issuer+serial or subject key identifier, content cipher AES-CBC, 3DES, RC2 or RC4. The file key is SHA-1 (SHA-256 for AES-256) of the 20-byte seed, every recipient blob and `FFFFFFFF` when metadata is plain; the recipient's permissions are bytes 21–24. Certificates come from the CurrentUser and LocalMachine `My` stores (with a private key); no match is a typed `PdfEncryptedDocumentException { CertificateRequired }`.
- **Decrypted copy for PDFium:** `PdfDecryptedCopyWriter` serializes every in-use object of a decrypted document into an in-memory unencrypted PDF (no `/Encrypt`, `/Crypt` filters removed, lengths recomputed, classic xref), so text search, selection, printing and annotations keep working through PDFium on certificate-encrypted files. The copy never touches disk: Save is disabled for it, file-path operations explain why they are unavailable, and Save As warns that the result is not encrypted. The writer round-trips all 2 913 corpus files (same page count, first page equal under PDFium).
- **Permissions enforcement (Table 22):** `PdfDocumentPermissions` (Abstractions) decodes `/P` per revision (R2: bits 9–12 follow bits 5/6) or the recipient's permissions; the owner password or an unrestricted recipient lifts everything. The view model refuses print, copy, export text/images, OCR text, annotate, form fill, edit/redact, organize/merge/split/extract and read aloud (accessibility bit) with an explanation; the status bar shows a lock with the restriction summary; printing without the high-quality bit is limited to 150 dpi.
- The viewer passes the password PDFium accepted to the vector document, including the lazy open after an engine switch; it is held for the open document only.
- Tests: a test-side encryptor (independent writer implementation) produces RC4-40/R2, RC4-128/R3, RC4-128/R4, AES-128/R4, AES-256/R5 and AES-256/R6 files; each opens with user and owner passwords, is refused without one, renders identically to the unencrypted document and like PDFium opened with the same password, and survives mutation fuzzing. The same encryptor builds public-key files (s4 RC4, s5 AES-128/256, several recipients, SKI and OAEP recipients, restricted and unrestricted); each opens only with a recipient certificate, renders identically to the unencrypted document, and its decrypted copy opens in PDFium. `SecuredDocumentTests` cover the viewer rules end to end.

### Vertical writing
- Identity-V and `/WMode 1` CMaps (named or embedded): each glyph's position vector (`/W2`, `/DW2`) is placed on the current point, the point advances by W1y (TJ adjustments apply vertically), glyph Y offsets reach both backends, and selection boxes follow the column.
- Sideways text in columns (UAX #50): Latin letters, digits, Greek, Cyrillic and other characters whose Vertical_Orientation is R are drawn turned 90° clockwise, reading top to bottom; U and Tu characters (ideographs, kana, Hangul, full-width forms) stay upright; Tr characters (brackets, the long vowel mark) use the font's vertical form (GSUB `vert`/`vrt2`) where it has one, else turn. The property comes from a compact range table compiled from UAX #50 (`Editing/VerticalOrientation.cs`, no data loaded at run time).

### Interactive forms and digital signatures
- **Forms** (`Forms/`): AcroForm fields read with inheritance; appearances regenerated for text, comb, multi-line, password, combo and list fields, and `/AS` for buttons. Each commit is an incremental revision (`Document/PdfIncrementalWriter`, classic or xref-stream sections) that both engines reload. PDFium draws widgets again through a form-fill environment and `FPDF_FFLDraw`. The viewer puts native, accessible editors over each widget.
- **Signing** (`Signatures/PdfSigner`, `PdfCmsSigner`): PAdES (`ETSI.CAdES.detached`) as an incremental update; a new or existing field with a visible appearance; certification (DocMDP 1-3); an optional RFC 3161 timestamp through a client the caller supplies (the only network request, opt-in, sending only a hash).
- **Validation** (`Signatures/PdfSignatureValidator`), with no network: integrity over the byte ranges; the chain at the signing (or timestamp) time; timestamps; later revisions classified (signatures, form fields, annotations, metadata or other) and weighed against the certification level. The viewer shows a verdict banner and a Signatures panel.
- Saving annotations on a signed document is incremental, so its signatures stay valid.
- **Long-term validation**:
  - PAdES-B-LT adds a DSS with the certificates, OCSP responses and CRLs each signature needs.
  - PAdES-B-LTA adds RFC 3161 document timestamps (`Signatures/PdfDocumentTimestamp`), each covering the validation data before it. A timestamp is accepted only when it was granted, its imprint and nonce match the request, and its signature verifies. Renewal is another timestamp over the last.
  - Validation reports each signature's level (B-B, B-T, B-LT, B-LTA) and when its archive timestamp needs renewing.
  - A document timestamp is a permitted change at every certification level. A "timestamp" with a visible appearance is not treated as one.
- **Signature appearances** (`Signatures/PdfSignatureAppearance`): text only, name and details, picture and details, or picture only, with a choice of details. A picture is chosen from a file or drawn in the signing dialog, kept with transparency, and remembered on the computer only if asked. Names Helvetica cannot show are set in an embedded installed font.

### Password protection
- `Security/PdfEncryptor` encrypts a document with the Standard security handler:
  - AES-256 (V5, R6, with /Perms) by default, or AES-128 (V4, R4); never RC4;
  - an open password and a permissions password, SASLprep'd (RFC 4013) and truncated to 127 bytes of UTF-8;
  - the permissions Acrobat offers: printing (none, low or high resolution), changing, copying, copying for accessibility, commenting, filling forms and page assembly;
  - metadata optionally left in the clear.
  - The result is a full rewrite with a fresh /ID, which PDFium opens with the password and renders the same as the original.
- Remove Security writes an unencrypted copy, but only when the owner password is known or proven. Signed documents are changed only after confirmation, because their signatures break.
- Viewer: Tools > Protect with Password... and Remove Security..., each saving a copy. Document Properties shows the security method and permissions.

### Accessibility check (PDF/UA-1)

### Make Accessible (auto-tagging)
- `Accessibility/PdfAutoTagger` tags an untagged document for assistive technology, as Acrobat Pro's Make Accessible does. It writes a complete copy (`PdfFullWriter`), never over the original.
  - Page content: every text-showing operator, image and form XObject is put in a marked-content sequence with an MCID, and furniture is put in an `/Artifact` sequence. Furniture is headers and footers that repeat at the same height on other pages, page numbers, rules, other vector graphics, full-page background images and drop shadows. The original bytes are kept: the sequences are inserted between operators. Sequences never cross the document's own marked content, a text object's bounds or a `Q` that ends their state. An `/ActualText` span is wrapped whole, because a reader takes the innermost property list. Existing artifacts are kept. Old MCIDs (when re-tagging) are taken out, in forms too.
  - Structure: `Document`, then `H1`–`H6`, `P`, `L`/`LI`/`Lbl`/`LBody`, `Table`/`TR`/`TH`/`TD`, `Figure`, `Link`, `Annot` and `Form`, in reading order. Lines and paragraphs come from `TextBlocks`, with the invisible text of OCR layers included. Reading order is a recursive XY cut on the page as displayed, so `/Rotate` is honoured. Bands that share a gutter that no item crosses stay one column region. Note markers, indented first lines and hanging indents join their paragraph.
  - Headings: by size class relative to the body text (the size most characters use), and bold where the body is not. Levels never skip, and the first heading is H1.
  - Lists: two or more items that start with the same kind of label (bullets, `1.`, `a)`, `(iv)`), numbers in sequence, and not across columns. A label drawn by its own operator, or set apart as its own line, is `Lbl`.
  - Tables (conservative): ruled grids whose every row and column line runs the whole grid, and three or more rows of single-line cells that align by column (short cells; prose is refused). Each line must sit in one cell, and no operator may draw two cells. Anything uncertain stays `P`. A bold first row over a regular body becomes `TH` with `/Scope /Column`.
  - Figures: `/Alt` is a placeholder ("Image: alternate text needs review"), or none when the option is off. A `/Layout /BBox` attribute is written, and the result lists the figures for review.
  - Links: a `Link` element in its paragraph, with the text it covers where the operators that draw that text draw nothing else, and an `OBJR`. A link without `/Contents` gets its text or its URI. Annotations get `/StructParent` and pages get `/Tabs /S`.
  - Catalog: `/MarkInfo /Marked true`, `/StructTreeRoot` with a `/ParentTree`, `/Lang` (an option, by default the document's or `en`) and `/ViewerPreferences /DisplayDocTitle true`. The XMP `dc:title` comes from the document information, else from the first heading. A role map is not needed, because only standard types are written. `pdfuaid:part` is written only on request (`ClaimPdfUa`): the claim is a person's to make.
  - Refusals, as a typed `PdfAutoTagStatus`: already tagged (unless `Retag`), encrypted without permission to change (an encrypted document that may be changed stays encrypted with its own key), a page whose content cannot be read, and no pages. As a safety check, the tagged copy's text is compared page by page with the original's, and a difference refuses the result (`TextWouldChange`).
- Quality gate: the copy is checked with `PdfUaValidator`. Each failing checkpoint is classified as *human review* (the PDF/UA claim, a missing title, descriptions of links, annotations and form fields, alternate text when no placeholder is written), *outside tagging* (fonts, encryption, XFA, optional content, embedded files) or *not fixed* (a gap in the tagger). The result lists them per document, with what a person should review.
- Tests: `PdfAutoTaggerTests` (21) on generated documents: headings, three kinds of lists, two columns drawn row by row, a title over two columns, a turned page, a ruled table, an aligned table, prose that is not a table, an image, a full-page background, a link, repeated headers and footers, re-tagging, refusals, `/ActualText` and existing artifacts. Every fixture must extract the same text and draw the same pixels (WPF and Direct2D renderers, byte for byte), and leave no *not fixed* checkpoint. With embedded fonts and the claim, the copy passes every machine check. `MakeAccessibleTests` (5) cover the dialog.

Pixels equal on the first three pages 144/144. In an earlier run, one file differed once; it did not differ again in isolation (three runs) or in the next full run. The smoke now re-draws the original to tell renderer variation from a tagging change.
  - Left after tagging, by documents: 06-002 (no PDF/UA claim) 144, 06-003 (no title found) 5, 28-004/28-005/28-012 (descriptions) 5. Outside tagging: unembedded or inconsistent fonts (31-008 88, 10-001 38, 31-004 21, 31-010 3, 31-030 3) and 21-001 (1). - Viewer: Tools > Accessibility > Make Accessible. ### Print production (separations, Output Preview, preflight)
- Separations (`PrintProduction/`): the interpreter builds a *plate display list* (`PdfVectorDocument.GetPlateDisplayListAsync`). In this list, every colour is the ink it puts on one to three plates, drawn as gray or as the R, G and B channels. Any renderer then draws the plates; the engine uses `Direct2DDisplayListRasterizer`. Because the colour spaces are swapped, not the painting, images (JPEG and JPEG 2000 included), shadings, meshes, tiling patterns, Type 3 glyphs, form XObjects and printing annotations all separate. Soft mask groups keep their own colours, because they shape the paint and print no ink.
  - Ink model (`PdfInkModel`): DeviceCMYK and four-component ICCBased go on C, M, Y and K as they are. DeviceGray and one-component ICCBased go on K = 1 − gray only. Separation and DeviceN colorants named Cyan, Magenta, Yellow or Black go on that process plate. A spot goes on its own plate. When the spot plate is turned off (a model without it), the spot goes through its tint transform and alternate. `/All` paints every plate and `/None` paints nothing. Indexed spaces separate through their base.
  - RGB, Lab and the Cal spaces: the colour is shown in sRGB first, then separated by `CmykSeparation`. This is a numerical inverse of the DeviceCMYK conversion (the built-in SWOP model, or Adobe's profile when it is installed), sampled on a 17³ grid, with a medium-GCR black and a 300 % ink limit. On a 54-colour in-gamut grid the round trip is ΔE76 0.65 on average and 2.5 at worst. It is **approximate**: it is not Adobe's B2A table, there is no ICC device link and no output-intent conversion, and an ICCBased CMYK profile is assumed to be the output condition. For example, 50 % RGB gray becomes 33/26/27/33 and RGB black becomes 68/68/68/95.
  - Overprint: `/OP`, `/op` (which defaults to `/OP`) and `/OPM` are tracked in the graphics state. With overprint simulation on, each plate is drawn on its own, and an overprinting object is left out of the plates its colour does not paint. In mode 1, the plates of zero DeviceCMYK (or ICCBased CMYK) components of the current colour are also left out; images and shadings are excluded, as 8.6.7 specifies. Gray and RGB paint every process plate. With simulation off, every object knocks out. Without overprint, three plates share one render, except when the page uses a non-separable blend mode.
  - Transparency: separable blend modes and opacity composite exactly per plate, because the plate value is the subtractive complement that 11.3.4 blends. Non-separable modes (Hue, Saturation, Color, Luminosity) are per plate, which is an approximation.
  - `PdfSeparation`: 8-bit ink planes; the ink and total ink at a pixel; coverage against a limit (maximum, pixels and fraction over, their bounds); a single plate as gray or tinted; and a composite of the visible plates (the process plates through the DeviceCMYK conversion, spots multiplied in their appearance colour, an approximation).
  - `PdfColorantInventory`: the colorants the pages actually paint, found from paint events in content, forms, patterns, shadings, images and annotations. A spot defined in the resources but never used is not listed. Each spot has its pages and its appearance colour.
- Preflight (`PdfPreflight`, report `PdfPreflightReport` in the style of the PDF/A report): pages are interpreted as they print, and every painting operation is reported (`IPdfPaintObserver`) with its colour space, bounds, opacity, blend, soft mask, overprint, stroke width in page points, and the image's placed resolution and object number.
  - *Digital printing (basic)*: fonts not embedded (PP-1.1, error; fonts used only for invisible text are PP-1.2, information); images under 150 ppi (PP-2.1, error) or under 300 ppi (PP-2.2, warning); RGB content (PP-3.1); total ink over 300 % (PP-4.1), measured on plates rendered at 36 dpi with overprint simulated, or per painted colour when no rasterizer is given; strokes thinner than 0.25 pt (PP-5.1, zero-width lines included); transparency (PP-6.1/6.2, information); spot colours (PP-3.3); missing TrimBox (PP-7.1) and BleedBox (PP-7.2).
  - *PDF/X-1a readiness*: RGB (PP-3.1) and device-independent colour (PP-3.2), transparency (PP-6.1), fonts (PP-1.1), the GTS_PDFX output intent (PP-8.1), TrimBox or ArtBox (PP-7.3) and encryption (PP-8.2), all as errors. These are checks only: the report says so, nothing is converted, and passing is not a PDF/X claim.
  - Findings have a page, bounds in page space and normalised bounds for the viewer, an object number (images) and a measure. There are at most 25 per rule and page; the rest are counted. The text and JSON exports carry no page text. Font and spot names (resource names) are included.
- Viewer: *Tools > Print Production > Output Preview* opens a window of its own, so the main view is unchanged. It has a plate checklist with swatches, *Simulate overprinting*, *Total ink over* with a limit (300 % by default) that highlights the pixels over it, and the ink of every plate and the total under the mouse. It follows the main window's page. Hiding a plate recomposes without a new render; overprint and page changes render again. *Tools > Print Production > Preflight* has a profile choice and results by severity. Selecting a result goes to its page and highlights the object, and the report exports as text or JSON. Both windows have access keys, automation names and live regions.
- Tests: `PrintProductionTests` (16) on generated PDFs, with exact plate values drawn by Direct2D: a spot on its plate and through its alternate, overprint in mode 1 and mode 0 and simulation off, an overprinting spot over cyan with a non-overprinting stroke, rich black (240 % and 400 %, with coverage bounds), DeviceN with a process and a spot colorant, gray as K only, RGB through the model, a Separation image, colorants inside a form, a pattern, a shading and an Indexed image (and not an unused one), the composite against the normal render (at most 1 level apart for CMYK content), the normal display list unchanged, and preflight for both profiles, with and without a rasterizer, on a clean file and with no page text in the exports. `PrintProductionViewerTests` (4) cover both windows and their view models.

### Printing
- Pages print through Direct2D's print control, drawn by the same renderer as the screen, as vectors: text stays text in the spool and in Print to PDF output.
  - Each page is replayed into a command list at 300 dpi. What Direct2D must rasterise (transparency groups, soft masks, pattern cells) comes out at print resolution; since M9 nothing is drawn by PDFium, and annotations print by their Print flag (NoView ones included, ones without Print left out).
  - A command list has no pixels to read back, so page-level groups that composite with the page under them (blend modes other than Normal, non-isolated groups that blend or knock out) print as images of their area only. Their device rectangles are merged until none touch; each becomes a 300 dpi image of the page composited up to the group's end, rendered by the screen path. The page is replayed in passes around the images: content before an image is clipped out of its area (the image holds it composited, so semi-transparent content is not applied twice), and content after it draws over it as vectors. Groups nested in other groups composite on their parent's bitmap and need nothing extra. The page prints as one 300 dpi image when the areas cover more than 60 % of it or there are more than 16 of them (`PrintedPageKind` Vector, Mixed or Raster). A page that fails to print as vectors prints as an image of the screen rendering in the same job.
  - Feeding the backdrop to the Blend effect as a nested command list was rejected: XPS has no blend modes, so the print control rasterises the effect over its inputs' full extent (the whole page so far, text included), and knockout and non-isolated groups read pixels back with copies and arithmetic composites that would all need rewriting. Images of only the areas give the same output with the screen's verified compositing.
- The image path stays for documents that allow only low-quality printing (150 dpi), for "Print as image" (Advanced, in the print preview), and when the print control cannot be created or a vector job fails.
- Print jobs run off the UI thread, with progress and cancellation in the status bar. The preview offers fit, actual size or a custom scale, page lists (1-5, 8, 11-13), and says whether the job prints as vectors or images, and why.

### Redaction
- `Redaction/PdfRedactor` removes content rather than covering it:
  - text: glyphs under a mark go, and the rest keep their exact positions through `TJ` adjustments; invisible text goes too;
  - vector fills and strokes are cut to the area outside the marks;
  - image pixels under a mark are blanked in new image objects (JPEG through WIC; CCITT and JBIG2 stencils);
  - form XObjects and annotation appearances are rewritten recursively;
  - shadings are clipped away from the marks;
  - `/ActualText` and `/Alt` about removed text are dropped;
  - form fields touched by a mark are removed.
- The output is a full rewrite: only reachable objects, no earlier revisions, and the original encryption kept.
- `vectorpdf redact` over the 3,197-file corpus: 3,167 of 3,181 openable files clean, 0 with text left under the band, 2 malformed files refused. The viewer marks selected text, dragged areas or every search match, and applies them into a new copy.

### Searchable scans
- `Ocr/PdfTextLayerWriter` adds recognized words as invisible text (render mode 3) in a glyphless Type0 font whose ToUnicode map gives back any Unicode. Each word is placed on and stretched to its box, and follows `/Rotate`; it is written as an incremental update. The viewer recognizes only the pages without text (Windows OCR), shows progress and can be stopped, and makes the result searchable at once.

### Editing page text and images
- `Editing/PdfContentEditor` finds each page's paragraphs and images and edits them.
- Paragraphs: lines are grouped with their width, line spacing and alignment (left, centred, right, justified), and line ends that are real line breaks are kept. A drop shadow (the same text drawn twice, a hair apart) is edited as one paragraph.
- Edited text:
  - reflows within the paragraph's width and alignment; a single line grows along its baseline, and a word longer than the line overflows rather than being cut;
  - every character keeps the font, size, colour and spacing of the character it replaces (new characters take those of the one before them);
  - lines before the first change are untouched, unchanged glyphs keep their own codes, and once the text matches the old text again the rest keeps its exact glyphs, only moved if the paragraph grew or shrank.
- Characters the document's font lacks (subsets embed only the glyphs they used) are written in the installed version of the same font, else a font of the same kind, embedded as a TrueType subset (Type0, Identity-H, with widths and ToUnicode). Whole words switch font, never single letters.
- Kerning: glyphs that were side by side keep the spacing they had (the document's own kerning and tracking), even when their line is laid out again. New glyphs are kerned by their font's pair kerning (GPOS 'kern' pair adjustments, formats 1 and 2, also through extension lookups; else the legacy kern table): an embedded installed font by its glyphs, and a document font the way its installed original kerns (same PostScript name, or same family and style; a stand-in's kerning is never used).
- Vertical writing (Identity-V and other vertical CMaps): columns are paragraphs, read top to bottom and right to left, and edited down the column with the font's vertical advances. Characters the font lacks come from an installed font, set upright in the column, in their vertical forms (GSUB vert/vrt2) where the font has them; the installed font is embedded for vertical writing (Identity-V), so the column reads back as one paragraph. A column that grows continues in the next column to the left.
  - Sideways runs: characters UAX #50 turns (Latin, digits and the like) typed into a column are drawn turned 90° clockwise, centred across the column and advancing down it by their horizontal widths: in the column's own font under its horizontal CMap (Identity-H for Identity-V, a predefined CMap's -H for its -V: same codes, same glyphs), else an installed font. Ideographs stay upright, so "PDF 2026年" sets "PDF 2026" sideways and "年" upright. A letter replacing one the document set upright (Latin in a vertical font) stays upright like it.
  - Reading: horizontal glyphs drawn with a text matrix turned a quarter clockwise in the frame of a column (in the same font's horizontal form or any other font) are read as part of that column, in reading order, when they lie on its centre line; a turned run with no column glyphs on its line stays rotated horizontal text. Edits keep an existing sideways run's exact glyphs and baseline, and new letters next to it take that baseline. Content is written in reading order, so plain text extraction (PDFium) reads the column logically.
  - Tate-chu-yoko (horizontal in vertical, JIS X 4051 and W3C JLREQ): a run of one or two half-width digits (or "!!", "!?", "?!", "??") typed between characters that are not Latin is set upright, its glyphs side by side on one baseline, centred across the column and in one em of it, so "平成12年" sets "12" in one slot. The run is in the column's font under its horizontal CMap, the font of the unit it replaces, or an installed font (in its half-width or third-width forms, GSUB `hwid`/`twid`, where it has them); wider than an em, it is compressed to one with `Tz`. A single digit takes the column font's full-width digit where it has one (marked with `/ActualText` so it reads as typed), else it stands upright and centred. Longer runs, and runs next to Latin letters or spaces, stay sideways. `PdfContentEditOptions.TateChuYoko` sets the rule: `Off`, `TwoDigits` (the default) or `UpToThree`.
  - Reading tate-chu-yoko: up to four horizontal glyphs drawn upright side by side, no wider than about an em, centred on a column's centre line in the slot right after or before one of its upright glyphs, are read as part of the column in their own order (the slot is one em). Edits that leave the unit's characters alone draw it again exactly as it was (moved with the column if text before it changed); a changed unit is set again as one. Plain text extraction reads it in the column's order ("令和06年" reads 令和, 06, 年). Not done: units of letters typed in a column (they turn sideways), and producers that centre a unit far off the font's ascent and descent middle are read only when within a third of an em of the slot.
- New characters in a composite font's own glyphs: a one-byte code is no longer taken for a CMap that reads two, which had sent every new character in such fonts to an installed font.
- Right-to-left and cursive scripts:
  - text is shaped before it is drawn: bidirectional levels and reordering (UAX #9, without explicit embeddings), mirrored brackets, Arabic joining forms, and the font's substitutions (GSUB single, multiple and ligature lookups, and contextual and chained contextual lookups in all three formats, including extension lookups, for ccmp, isol/init/medi/fina, rlig, calt and liga);
  - marks are placed on their letters' anchors and do not advance (GPOS mark-to-base, mark-to-ligature and mark-to-mark), so vowel marks sit over and under the letters they belong to;
  - cursive attachment (GPOS 3, also through extension lookups, honouring the lookup flags such as IgnoreMarks): each letter's entry anchor is put on the exit anchor of the letter before it, along the line (advances and x offsets, for left-to-right and right-to-left runs) and across it (y offsets down the joined chain; with the RightToLeft flag the last letter of a word sits on the baseline and the earlier ones hang off it, as in Nastaliq). Marks follow their letters up and down the chain, and raised glyphs are drawn at their own height. Anchors of formats 2 and 3 are read as format 1 (contour points and device tables are not used);
  - a line of right-to-left text read from a page is put in reading order, glyph by glyph, so Arabic and Hebrew paragraphs are edited as they are read and drawn again in drawing order;
  - a cursive word that changed is shaped again as a whole in an installed font, because the document's glyphs for its letters are in the forms their old neighbours needed;
  - Indic scripts in new text (`Editing/IndicShaper`: Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada, Malayalam), as the OpenType Indic specification and HarfBuzz shape them:
    - syllables, base consonants, reph and pre-base matra reordering, and the basic features with their per-glyph masks;
    - final reordering, then the presentation features and GPOS (abvm, blwm, dist, kern);
    - v2 script tags fall back to v1 tags.
    - About 150 words across the nine scripts match Windows' own shaping in glyph ids, and in positions to within 1.5/1000 em (Nirmala UI).
    - Reordered syllables carry /ActualText, so they extract as typed.
  - Indic text in existing paragraphs: a changed Indic word is shaped again as a whole in an installed font, and glyphs drawn in a short /ActualText span (a syllable or ligature, within one line) read as that text and move together when their line is laid out again, so Hindi on a page is edited in reading order.
- Moved, edited and redrawn text is drawn right after the text-showing operator it replaces, even inside a text object (the text object is split, and the text position and line start restored), so stacking and clipping stay as they were.
- Text and images inside form XObjects (to any depth up to 8) are found where each drawing of the form puts them, and edited like the page's own. The drawing that has an edit gets its own copy of the form (a new object, with the names it inherits from where it is drawn, the fonts and images the edit added, and copies of the forms it draws), so other drawings of a shared form stay as they are. Paragraphs never span two drawings, since each uses its own resources. Content moved outside the form's bounding box is clipped by it, as the form's own content would be.
- Images are deleted, moved, resized, turned or replaced where they are drawn. A replacement keeps its own proportions within the old box. New text and new images (JPEG embedded unchanged; other formats lossless, with transparency) are added over the page. Results are written as an incremental update.
- `vectorpdf edit` over the 3,197-file corpus:
  - page 1's longest paragraph is redrawn unchanged, then one of its words is replaced;
  - 578 files edited cleanly: PDFium reads the new word back, and nothing changes outside the paragraph (575 before text inside form XObjects could be edited);
  - redrawing unchanged differs on 2 files, both from JPEG 2000 logos that decode differently from run to run;
  - 2 files with corrupt content streams are refused;
  - the other files have no paragraph on page 1 (conformance test files, and scans whose text is an invisible OCR layer).
- The viewer's Edit Text & Images mode (Ctrl+E):
  - outlines paragraphs and images; double-click edits text in place, in its font, size, colour and alignment;
  - drag moves, a drag on an image's corners resizes it (proportionally, unless Shift is held), and the context menu replaces or turns images;
  - Delete removes the selection, Add Text and Add Image place new content, and Ctrl+Z / Ctrl+Y undo and redo;
  - edits are in-memory revisions saved incrementally, and editing a signed document is confirmed first.

### Headers, footers, watermarks, backgrounds and Bates numbers

### Export to Word
- `Export/DocxExporter.ExportAsync` writes a .docx package by hand (System.IO.Compression and XmlWriter, no new packages); a file export goes through a `.partial` file, so a cancelled or failed export leaves nothing.
  - Text: paragraphs from `TextBlocks`, column by column, with each run's font, size, colour, bold and italic; subset names map to the Word family, and missing fonts get an `altName` so Word substitutes a similar face.
  - Layout: alignment, indents, exact line spacing and space before from page positions; underline, strike and superscript from the rules and offsets around the text; headings 1-3 from tags or from larger bold lines; bullets and numbers as real Word numbering.
  - Tables from tags (with spans), from ruling lines (merged cells, borders, shading) and from text aligned in columns; images inline or anchored at their page position; repeated headers and footers with PAGE and NUMPAGES fields; hyperlinks, section columns, right-to-left paragraphs and East Asian font slots.
  - Page fidelity: each PDF page stays one Word page as far as Word lets it.
    - Lines fit: where the font Word will use (the installed one, or the stand-in of its kind) sets a line wider than the room the page gave it, the paragraph is condensed (character spacing, then horizontal scale). Lines that start at very different places keep the page's line breaks.
    - Heights: one-line paragraphs set closer than their line height take the distance to the next line; table rows tighter than their text close the space above it, then the line height. What Word still makes taller (rows that grow, items that overlap on the page) comes out of the space after it. A page whose estimated height is over 95 % of its text area has its gaps, then its line heights, closed up.
    - Headers and footers: text repeated on 20 % of the pages (at least 3) at the same place is a header or footer, and pages can differ (odd and even pages, parts, front matter). Each combination is written once, and each section uses its own, so pages without one show none. Page numbers are PAGE fields, and where printed numbers start again (A-1, chapter numbers such as 2-14, roman then arabic) a section starts with that number and format. Where body text runs into a header's or footer's band, that one is set in text boxes, so it takes no room from the body.
    - The last paragraph of a page does not keep with the next page; tables one after another are kept apart; tables side by side become one row of a layout table.
  - Contents lines: dot leaders (also a title block beside a column of page numbers) become a right tab stop with a dot leader at the number's right edge.
  - Drawings: rectangles and straight lines become Word shapes at their places (behind the text); rules and fills that are already table borders, underlines or shading are not drawn twice. Other drawings (curves, charts, maps, gradients, patterns) are grouped by what touches, and each group becomes a picture of only those drawings, made by the vector renderer at 150 dpi (`DocxExportOptions.Renderer`, white left see-through), anchored behind the text in drawing order. Without a renderer they are left out.
  - Turned text: a text box at its place, turned as the text is, with the page's lines and fitted to the text's length. Pictures beside other content are anchored at their place instead of the flow.
- Viewer: File > Export > Word Document (.docx), with per-page progress and cancel; drawings are rendered with Direct2D. Tool: `vectorpdf docx [--word]` (counts and coverage only, no document text). With `--word`, Word (when installed) opens each .docx read-only, lays it out and counts its pages; Word's settings are not changed.
- GovDocs (284 files): 274 exported with 0 errors (10 encrypted or empty), and Word opens all 274 without repair.
  - Exact-word coverage against PDFium 98.48 % overall, in-order coverage median 99.97 % (unchanged by the fidelity work).
  - Pages in Word (Word 16 on Windows, fonts installed there): 8,267 for 7,740 PDF pages (1.07 times, was 10,802, 1.40 times). Per file the median ratio is 1.000 (was 1.370); 175 of 274 files keep their page count exactly (63.9 %, was 44), 196 are within 5 % (was 57), and 11 run over 1.5 times (was 101).
  - 1,663 text boxes, 52,572 shapes and 3,361 pictures of drawings, in 223 files.
- Not yet: Type 3 fonts without Unicode export no text. Fonts that are not installed are measured as their stand-in (Word may choose another). Tables cannot shrink, so a page of tall rows can still run over. Rectangles and lines inside a table are left to the table's borders and shading.

### Reduce File Size
- `Optimize/PdfOptimizer` saves a smaller copy that looks the same:
  - a complete rewrite of what the catalog reaches, so unused objects go;
  - identical fonts, images and other shared resources are stored once. Pages, annotations, fields, outline items, structure elements and layers keep their identity;
  - general-purpose filters are replaced by the strongest Flate where that is smaller, and image codecs are kept;
  - objects are packed into object streams with a cross-reference stream. PDF/A-1 documents keep a classic table, a 1.4 header and readable metadata;
  - page thumbnails and applications' private data are dropped;
  - optionally, images shown above a resolution are downsampled to it by averaging, soft masks with them. JPEG images go through the host's codec, and CMYK, indexed and colour-keyed images are left alone.
- Encrypted documents are reduced and stay encrypted the same way:
  - objects are read through the open document's security handler, and the copy is encrypted again with the same file key. Loose objects and object streams are encrypted; the cross-reference stream and the encryption dictionary are not;
  - the original encryption dictionary is carried over unchanged: revision (R2 to R6), cipher (RC4 40 and 128-bit, AES-128, AES-256), /P, /EncryptMetadata, and /O, /U, /OE, /UE and /Perms. The first /ID string is kept, because the key of R2 to R4 derives from it;
  - both passwords therefore keep working, even when the document was opened with the open password only. No password is stored or written, and messages never contain one;
  - the rewrite is a change: it needs the permissions password (used to open, or given as `PdfOptimizeOptions.OwnerPassword`), or /P bit 4 (changing the document). Otherwise it is refused with a clear message;
  - certificate-encrypted (public-key) documents are reduced the same way by the engine when the recipient may change them. The viewer only holds a decrypted copy of them, so it does not offer Reduce File Size for them;
  - tests build R2, R3, R4 (RC4 and AES-128), R5 and R6 documents in-test. The copies are smaller, open with the same passwords, keep the permissions and dictionary entries, and render the same as the original in our engine and in PDFium.
- Signed documents are saved only after confirmation, because their signatures break.
- `vectorpdf optimize` over the 3,197-file corpus, lossless settings:
  - 3,176 files are rewritten, and 21 are skipped (encrypted or repaired);
  - 311 MB become 266 MB (86 %), and the GovDocs files lose about a third of their size;
  - PDFium reads the same text on the first pages of every file, and they render as before (checked after the JPEG 2000 fix).
- Viewer: Tools > Reduce File Size... offers the image presets and saves a copy. An encrypted document is reduced with the password it was opened with. When its permissions forbid changes, the viewer asks for the permissions password.

  - Missing widget appearances are generated from the field values, and missing annotation appearances are generated as Acrobat draws them (`Annotations/PdfAnnotationAppearances`).
  - Fonts that are not embedded are embedded from the installed fonts. A matching family is preferred, with PostScript aliases such as Palatino to Palatino Linotype and AvantGarde to Century Gothic.
  - The document's widths are written into each embedded program's metrics. Layout never moves, and inconsistent widths in fonts that were already embedded are repaired the same way.
  - An output intent is added: a generated sRGB v2 profile, or the Windows CMYK profile for CMYK documents so their CMYK stays device colour. Default colour spaces and ICC alternates are added where needed.
  - XMP is rebuilt from the valid existing properties plus the document information.
  - Scripts, forbidden actions and annotations, transfer functions, OPI, PostScript and external stream data are removed, along with filters PDF/A does not allow.
  - Optional content is named and ordered.
  - PDF/A-3 keeps embedded files as associated files; PDF/A-2 removes them.
  - Codes whose glyph the font program lacks (they draw .notdef) are taken out of the text operators of pages, forms and appearances (`PdfA/NotdefGlyphRemover`). Each is replaced by a TJ adjustment, so every other glyph stays exactly where it was, and the rest of each stream is kept byte for byte.
  - A glyph two codes share with different /Widths is copied for one of them (`PdfA/TrueTypeGlyphCopies`), and that code is remapped through the font's cmap, private-use names or CIDToGIDMap. Both widths then hold.
  - PDF/A-1b:
    - Transparency is flattened (`PdfA/TransparencyFlattener`) when the converter is given a rasterizer (`IPdfPageRasterizer`; the viewer and the tool pass `Direct2DPageRasterizer`, which since M9 draws every page itself, regions it cannot reproduce exactly by best effort; `vectorpdf pdfa-convert --pdfium-fallback` still has PDFium draw them). Without one, such documents are refused as before. Hidden layers are still refused: they would show.
      - Transparent objects are found by walking the content (forms included): anything drawn with a soft mask, alpha below 1, a blend mode other than Normal or Compatible, a soft-masked image, a transparent pattern or Type 3 glyphs that use transparency, and transparency groups drawn with alpha, a blend mode or a soft mask. The display list's own transparency bounds are a check on the walker: an area it misses is added.
      - Their bounds are merged into regions on the page's pixel grid; when the regions cover 60 % of the page or more, the whole page is one region.
      - Each region is drawn from a copy of the page with everything up to the last transparent object: 300 dpi, 600 dpi where text is drawn into it, at most 30 million pixels each. The image is lossless (Flate with PNG predictors, DeviceGray when grey; run-length when a blank area would compress past the 500:1 decompression guard).
      - The content is written three times in one stream: what is under the images, the images, and what is drawn after the last transparent object, over them. Operators that belong to another copy keep only their effect on the state (paths end with `n`, text keeps its advance in a `TJ`), so clipping and text positions are unchanged. Everything outside the regions stays vector, and text above transparency stays real text over the image.
      - Text that was itself transparent stays in its operator as invisible text (rendering mode 3), so search and copy still find it in place; opaque text under an image keeps its operator, covered by the image.
      - Groups, soft masks, blend modes and alpha are removed from what remains; forms are copied per drawing when their drawing changes. Images, forms, patterns and graphics states that are no longer drawn leave the page's resources, and so the file.
      - Annotations: a translucent annotation (/CA), or one whose appearance draws transparency (a Multiply highlight), gets an image of how it looked over the page as its appearance; its comment and other entries stay. Appearances with only opaque groups or unused alpha are cleaned without an image, form field widgets included.
      - The result reports the pages, regions, resolutions and renderer (`PdfAConversionResult.Flattening`). Tools > PDF/A shows it in the summary and the list of changes.
    - Otherwise the converter writes a 1.4 header, re-encodes JPEG 2000 as Flate, and removes optional content, embedded files and the annotation types PDF/A-1 forbids.
    - It keeps or writes /CharSet and /CIDSet, and writes XMP 2004 with the preferred prefixes.
  - The result is validated, and anything that could not be fixed is reported.

### Create PDF
Acrobat's Create PDF, done on the machine: no cloud conversion, no telemetry, nothing installed.
- **Writer** (`Create/PdfDocumentWriter`): a new document is written to the output stream an object at a time. Each page is finished before the next is given, and deflated data goes out as it is compressed, with its /Length in an object of its own, so a thousand-page scan never holds more than one picture in memory. `Finish` writes the page tree, the catalog (with DisplayDocTitle when there is a title), the information dictionary (Title, Creator, Producer, dates), a classic cross-reference table and an /ID hashed from the file. Pages have a /MediaBox and nothing they do not use.
- **Images** (`Create/PdfCreateImage`, `PdfImagePageLayout`, `PngPredictor`; WIC side `PdfEngine.Vector.Windows/Create/WicImageReader`, `ImagesToPdf`):
  - a JPEG that needs no change is never decoded: `JpegHeader` reads its markers (frame, components, Adobe APP14, ICC profile in APP2 chunks, EXIF orientation and resolution, JFIF density), and its bytes become a DCTDecode image. Baseline, extended and progressive 8-bit frames pass through; lossless, arithmetic-coded and 12-bit JPEGs are decoded. Adobe CMYK JPEGs get /Decode [1 0 ...] for their inverted samples;
  - other pictures are decoded with Windows Imaging Component a frame at a time (every page of a TIFF; WebP, HEIF and the rest when their decoders are installed) and written losslessly with Flate and a PNG predictor chosen per row. 1-bit stays 1-bit, 2- and 4-bit grey stay as they are, 16-bit grey and RGB stay 16-bit, palette images without transparency keep an /Indexed palette, CMYK stays CMYK, and transparency becomes an /SMask;
  - an ICC profile from the picture becomes an /ICCBased colour space when its colour space matches (written once however many pages use it); otherwise device colour;
  - EXIF orientation (all eight) is applied by the image matrix, not by turning pixels, so a turned JPEG still passes through;
  - options: the page fits the picture at its resolution (up to 200 inches), or goes on paper (A4, Letter, Legal; landscape for a landscape picture) inside margins, fitted or filling and cropped; greyscale; JPEG recompression at a chosen quality.
- **Plain text** (`Create/PdfTextDocument`): our own layout. The bytes are read by their byte-order mark, as UTF-8 when valid, else as Windows-1252. Lines wrap at the last space that fits, tabs go to the next stop, and a form feed starts a page. The text is in Consolas (or another installed face) embedded as a subset with widths and a ToUnicode map, and characters it lacks come from the system's fallback faces. The text is extractable by the native text service.
- **Combine** (`PdfPageAssembler.Merge` with `SourceTitles` and the new `PdfAssemblyOptions.Info`): one outline item per source named after its file, holding the source's own outline. Pictures and Office files become PDFs first; protected PDFs ask for their password.
- **Viewer** (`Services/CreatePdfService`, `ViewModels/CreatePdfViewModel`, `ScanViewModel`, `MainViewModel.CreatePdf`):
  - File > Create PDF > From Images, From Scanner, From File and Combine Files. The result is written beside its target and moved into place when complete, so a stopped or failed run leaves no file. It opens in a new tab;
  - the From Images and Combine Files window has a file list (add, drop files from Explorer, drag to reorder, Alt+Up/Down, Delete), the options, a progress bar and Stop;
  - Make Searchable runs the same path as Tools > Make Scanned Pages Searchable on every page without text (Windows OCR, `PdfTextLayerWriter`), and the update is then folded into a compact file. PDF/A-2b runs `PdfAConverter` on the result. With neither, images stream straight to the file.
- **Scanner** (`Services/Scanning`): `IScannerService`, with `WiaScannerService` over Windows Image Acquisition 2.0 through its scripting interface (`WIA.DeviceManager`, late bound, on an STA thread of its own). It lists scanners without connecting to them, because a network scanner that is off can take minutes to answer. Their flatbed, feeder and duplex are then read in the background. It sets intent, data type, depth and resolution, selects the flatbed, feeder or duplex feeder (or the driver's child item for each), and transfers pages as PNG when the driver can, else in its own format, until the feeder is empty. Driver errors (empty feeder, jam, busy, offline, cover open, service stopped) become plain messages, and with no scanner it says so. Pages wait in a private temporary folder until the PDF is made. Stop does not wait for a driver stuck in a call. Tests use a fake scanner with a duplex feeder.
- **Office** (`Services/OfficeConverter`): Word, Excel and PowerPoint through COM (late bound), with each application's own ExportAsFixedFormat (PowerPoint falls back to SaveCopyAs as PDF). The file is opened read-only, not added to recent files, links not updated, without repair, and with macros disabled (`AutomationSecurity` force-disable, an instance setting). The instance is hidden, and only its own alerts are turned off. It is quit only if this conversion started it: a PowerPoint the user already has open is used and left open. Without Office, a text file uses our layout, and other types say clearly which Office application they need.
- **Tests**: `CreatePdfTests` (engine) encode pictures in-test with WIC and check page counts, sizes and turns, byte-identical JPEG passthrough (with EXIF orientation 6 and with an APP2 ICC profile), lossless PNG pixels and alpha, multi-frame TIFF with grey and 1-bit frames, palettes, greyscale, JPEG recompression, paper layout, a damaged image named in the error, PDF/A-2b conversion that validates, text layout and extraction, and combining with outline items. `CreatePdfViewerTests` check the menu and commands, a new tab, recognition (a fake recognizer, and real Windows OCR on a rendered phrase when a language is installed), PDF/A, Stop, a source never overwritten, a fake duplex feeder (7 pages over three scans), no scanner and the service stopped, text without Office, Word without Office, combining, and password-protected sources.
- **Office smoke test** (`PDFVIEWER_OFFICE_SMOKE=1`, because it starts Office): a .docx, .xlsx and .pptx made by our own exporters from a synthetic PDF convert through Word, Excel and PowerPoint 16 on the development machine. Each PDF has the text, and no Office process is left behind.
- Not yet: no TWAIN (WIA only), and no scanner preview or crop. The scanner path was tested with the fake scanner and the device listing only, not with a physical feeder. Office files with an open password fail with a message; Word and Excel do not prompt, but PowerPoint may. Plain text is not shaped (Arabic joining, Indic reordering), although it copies correctly. With Make Searchable or PDF/A, and when combining, the document is held in memory while it is finished. Printing to PDF for file types Office does not open is left to "Microsoft Print to PDF".

### Measuring and stamps
Acrobat's Measure tools and Stamp tool, written as the annotations Acrobat reads.
- **Measure dictionaries** (`Annotations/PdfMeasure`): a rectilinear `/Measure` (ISO 32000-2 12.9, Table 266) with its number format arrays (Table 268: `/U`, `/C`, `/F` D, F, R or T, `/D`, `/FD`, `/RT`, `/RD`, `/PS`, `/SS`, `/O`) is read and written. A chain of formats shows a value in several units ("5 ft 3 in"), carrying a rest that rounds up to a whole unit. Distances use `/X` for x, and `/Y` with `/CYX` for y when given, then `/D` from the x unit; areas use the same factors squared and `/A`; angles `/T`. `PdfMeasure.FromScale` makes the measure for a scale such as 1 in = 10 ft: one point is (1/72 in) × real/paper in the real unit, in pt, in, mm, cm, m, ft, yd, km or mi.
- **Viewports** (`PdfViewports`): a page's `/VP` array; a point is measured in the last viewport that contains it (12.9.2). Geospatial measures (`/GEO`) are flagged and not modelled.
- **Measurement annotations** (`PdfMeasurements`): a distance is a Line with `/IT /LineDimension`, `/L`, `/LE [/OpenArrow /OpenArrow]` and `/Cap true`; a perimeter a PolyLine with `/IT /PolyLineDimension`; an area a Polygon with `/IT /PolygonDimension`. Each has `/Measure`, the result as `/Contents`, `/Subj` (Distance, Perimeter or Area Measurement) and a `/Rect` that holds the points, arrow heads and label. `PdfAnnotationReader` reads `/Measure` and `/Cap` back; `PdfAnnotationEditor` writes them, and keeps a measure it could not model.
- **Appearances**: the generator (`PdfAnnotationAppearances`) draws the line's caption as before, and a perimeter's or area's result on a white tab at the last segment's middle or the polygon's centroid.
- **Snapping** (`Annotations/PdfSnapIndex`): every filled and stroked path of the page's display list, in page space (transforms applied), as segments in a uniform 24 pt grid. Curves are followed as 12 chords. A query returns the nearest end point, else the nearest middle of a straight line, else the nearest point on a path, within the tolerance (7 screen pixels in the viewer).
- **Stamps** (`Annotations/PdfStamps`, `PdfStampAppearance`):
  - the catalogue uses the names of ISO 32000-2 Table 184 (Approved, Confidential, Draft, Final, ForComment, NotApproved, ForPublicRelease, NotForPublicRelease, Expired, TopSecret, AsIs) and of Acrobat's Standard Business set (SBCompleted, SBInformationOnly, SBPreliminaryResults, SBReviewed, SBRevised, SBVoid), plus Received. Dynamic stamps are Approved, Confidential, Received, Reviewed and Revised with a second line "By name at HH:mm, d MMM yyyy";
  - the design is our own: a rounded band in the stamp's colour (red for refusals, green for approvals, blue otherwise) on a 12 % wash of it, an inner hairline, the label in bold capitals fitted to the box, and for a dynamic stamp a rule and the second line. Text is in the installed fonts, embedded as subsets;
  - custom stamps are a picture (an image XObject with its soft mask) or a page of another PDF (its content and resources copied into the document, upright as the page is seen);
  - a turned stamp is drawn upright at its own size and turned by the form's `/Matrix`; its `/Rect` is the turned box, so 12.5.5 fits it without distortion. `PdfAnnotation.AppearanceRotation` reads the turn back;
  - a stamp that is changed (moved, resized, its comment edited) keeps its appearance; only its rectangle changes;
  - `PdfStamps.Preview` puts a stamp on a page of its own size, on white or on black, so the viewer shows the engine's own drawing (alpha from the two renders).
- **Viewer** (`ViewModels/MainViewModel.Measure`, `MainViewModel.Stamps`, `Views/MainWindow.Measure`, `Services/MeasureScaleStore`, `Services/StampLibrary`):
  - Tools > Measure > Distance, Perimeter, Area, Set Scale and Units, Snap to Content. A click places a point; a distance ends at its second point, a perimeter or area on a double-click or Enter. Backspace takes back a point, Esc drops the measurement (again: stops the tool), Shift places a point without snapping. The canvas shows the points, a rubber band and a snap marker (square: end point, triangle: middle, circle: on a line);
  - the info panel shows each segment's length (and an area's closing side), the total, the area, the angle of the last segment, the pointer's x and y from the page's top-left in the measure's units, what it snapped to, and the scale and where it came from;
  - the scale is the page's viewport where one covers the first point, else the one set for the document, else 1 in = 1 in. A set scale is remembered per document in `%LOCALAPPDATA%\PdfViewerNative\measure-scales.json`, keyed by a SHA-256 of the file's path, so the file is not named; the last 200 are kept;
  - Comment > Stamp: Dynamic, Standard Business, Custom (the library), Create Custom Stamp from Picture or from a PDF Page, Remove Custom Stamp, Rotate New Stamps (0, 45, 90, 180, 270, 315 degrees) and Name on Dynamic Stamps. The name is asked for the first time a dynamic stamp is chosen and kept in `stamps.json`; nothing is sent anywhere;
  - the stamp library is `%LOCALAPPDATA%\PdfViewerNative\Stamps`: a picture is kept as the PNG or JPEG it is (after decoding it), and a PDF page as a one-page PDF of that page alone (`PdfPageAssembler.Extract`, without outline or form). Encrypted PDFs and files over 20 MB are refused;
  - a click places a stamp at its usual size (wider for a longer label), a drag gives its box (a picture keeps its shape inside it);
  - measurements and stamps are `AnnotationModel`s (types Measurement and Stamp), so adding, deleting and changing them go through `CommandHistory` like every comment. `NativeDocumentServices.IsManaged` decides what the viewer reads and writes, in loading and saving alike: the earlier types, every stamp, and lines, polylines and polygons with a rectilinear `/Measure`. Other lines and polygons stay the document's own;
  - the XFDF export writes line (`start`, `end`), polyline and polygon (`vertices`) and stamp (`icon`) elements. PDFium mode (developer builds) does not save measurements or stamps;
  - one key behaviour, no new shortcut: Enter, Backspace, Esc and Shift while measuring, Esc while placing a stamp. `MenuShortcutTests` still passes (no menu gesture added).
- **Tests**: `MeasurementTests` (engine, 11): scales and units against hand-worked values (1 in = 10 ft, 1:1000 in mm to m, 2 cm = 5 km, 1 in = 1 mi, 1 pt = 1 pt), perimeter, area, angle, `/Y` with `/CYX`, decimal, fraction, round, truncate, separators and label position, feet-and-inches chains, viewports (the later one wins, geospatial flagged), the measure dictionary through save and read with Acrobat's keys, change and delete, flattening, and snapping (end points, middles, paths, transforms, closed paths, curves). `StampTests` (engine, 10): the catalogue, a dynamic stamp's dictionary and two-line appearance and its pixels, a turned stamp's matrix and pixels, a picture stamp with its soft mask, a PDF-page stamp drawn from its own resources, a moved stamp keeping its appearance, flattening, PDF/A-2b conversion (compliant, stamps kept), printing, and the preview page. `StampParityTests` (Skia, 2): designed and turned stamps, a picture stamp and an area measurement drawn by Skia against Direct2D (budgets: mean 2.5 and 1.5 % bad pixels for the small dynamic line, as `TextParityTests.SmallBodyText`; mean 1.5 and 2 % otherwise). `MeasureAndStampViewerTests` (viewer, 12): the measuring flow with the info panel, undo and redo, perimeter and area, snapping on a page, a viewport's scale, the scale remembered per document (and the file not named), save and reopen of measurements and stamps (standard, dynamic, a custom picture and a custom PDF page), a reopened document saved untouched keeping its stamps, and the tools excluding each other.
- Placed measurements and stamps are edited with the annotation edit layer (see "Annotation edit handles" below).
- Not yet: geospatial (`/GEO`) measures, `/Path` measurements, slope (`/S`) and the Acrobat comment-panel measurement details are not supported; the feet-and-inches display is read from documents but the scale dialog offers one unit; Acrobat's own stamp artwork is not reproduced (by design).

### Annotation edit handles
A placed annotation is selected and changed on the page, as in Acrobat.
- **Selecting**: a click on an annotation selects it (a drag over it still selects text); a double-click or Enter opens its comment; Tab and Shift+Tab go through the page's annotations in drawing order, and past the last one Tab moves on through the window. Esc lets go.
- **Handles** (`Views/AnnotationEditLayer`): the outline (drag to move), eight corner and edge handles, a rotation handle above a stamp as the page is seen, and a handle on each point of a measurement or of a drawing with up to 24 points. The look is the content edit layer's. The layer is in unrotated page space at screen scale, so handles are 9 px at any zoom and turn with the page; resize cursors follow the page's rotation. A pane automation peer lists the handles as named thumbs ("Resize handle, top left", "Rotate handle", "Point 1 handle").
- **Geometry** (`ViewModels/MainViewModel.AnnotationEditing`), in the page's points: a move keeps a box on the page; a resize keeps the opposite corner or edge (Shift keeps the proportions; stamps keep them by default, a picture always, and a stamp turned at an angle always); a drawing's points and a markup's line boxes scale with the box. A turn is about the stamp's centre, counter-clockwise in default user space, snapped to 15 degrees with Shift; the box becomes `PdfStamps.RotatedBounds` of the stamp's own size. A measurement's point snaps through `PdfSnapIndex` (Shift: no snapping) and the measurement is made again with `PdfMeasurements.Create`, so its result (`/Contents`), its box and its label follow the points. Arrow keys nudge by 1 pt (Shift: 10 pt), turned back through the page's rotation so Right moves it right on screen at 0, 90, 180 and 270 degrees.
- **Undo**: a drag changes the model as it goes and is one `CommandHistory` step when it ends ("Move Stamp", "Resize Ellipse", "Rotate Stamp", "Move Measurement Point"); Esc during a drag puts it back with nothing recorded. Each nudge and a Delete are one step.
- **Saving** goes through `NativeDocumentServices` and `PdfAnnotationEditor` as before. Changed measurements, shapes, ink and markup get new appearances from `PdfAnnotationAppearances`. A loaded stamp keeps its own appearance: moving or sizing it changes only `/Rect` (#94's rule); turning it sets `PdfAnnotation.AppearanceTurn`, and the editor writes a copy of its form with the turn added to `/Matrix`. `PdfAnnotation.AppearanceSize` reads a turned appearance's upright size back, so a loaded turned stamp keeps its own width and height.
- **The page while it is edited**: the page renders annotations from the file, so a loaded annotation that is changed or deleted would still show where it was. `PdfVectorDocument.SetHiddenAnnotations` leaves such annotations (by object number) out of the screen display lists, not out of printing; the viewer hides every loaded annotation that differs from the file, draws the pages it touches again, and the overlay draws the changed one. A loaded stamp's overlay is `PdfStamps.PreviewOfAppearance`: its own appearance on a page of its own, turned as it will be saved. Undoing back to the file's state gives it back to the page.
- **Tests**: `AnnotationEditEngineTests` (engine, 4): a kept stamp turned through a new form with the turn in `/Matrix` and its pixels, the upright size of a turned appearance, hidden annotations left off the screen but printed, and the preview of a kept appearance. `AnnotationEditingViewerTests` (viewer, 20): move, resize (free, proportional, to the smallest size), Esc during a drag, saved and reopened shapes; a stamp resized in proportion and turned (with Shift snapping), a new turned stamp saved, a loaded stamp kept when moved and given a new `/Matrix` when turned; undo giving a loaded annotation back to the page; a measurement's point moved, snapped and unsnapped with its result measured again, an area's point saved and reopened with a new appearance; point handles on a small drawing and scaling of a freehand one; arrow-key nudging at 0, 90, 180 and 270 degrees; a measurement and a stamp dragged on pages turned 90 and 270 and saved; Delete and Tab; a document that forbids comments; and the layer's handles, their size at two zooms and their automation peers.
- Not yet: handles sit on the box that a turned stamp covers (its own outline is drawn dashed inside); a multi-line highlight, a note and a measurement move but do not resize; a freehand drawing's points are not edited one by one; several annotations cannot be selected at once.

### Native document services (M9)
The document-level services no longer need PDFium (`PdfEngine.Vector/Services`). In Auto and Vector modes the viewer uses them for properties, bookmarks, permissions, annotations, page organisation, merging, splitting and embedded files; PDFium mode keeps the PDFium path.
- **Reading:** document properties as FPDF_GetMetaText gives them (PDFDocEncoding, UTF-16 and UTF-8 text strings, dates), the header version, the security revision and /P as FPDF_GetDocPermissions reports it, and every page box. The outline and links resolve explicit, named (name tree and catalog /Dests) and go-to destinations, URI actions with /URI /Base, and remote and launch file names, with PDFium's rules for malformed entries. Embedded files are listed from the name tree and from file attachment annotations; a file shown both ways is one file.
- **Annotations:** every type is read with its properties: subtype, rectangle, colours, opacity, contents, author, subject, unique name, dates, flags, border, ink, quadrilaterals, line, vertices, line endings, icon, free text appearance, pop-up, and replies. They are created, changed, deleted (with their pop-ups and, optionally, replies) and flattened (FPDFPage_Flatten: the normal appearance drawn into the page, links and hidden annotations kept) as incremental updates. Encrypted documents get encrypted updates. New and changed annotations get appearance streams from `PdfAnnotationAppearances`.
- **Viewer saving:** annotations the user did not touch are kept as they are, with their appearance, pop-up, replies and rich text. Changed ones keep what the viewer does not model. A signed document gets an incremental update; any other is written whole, so deleted comments do not stay in an earlier revision. Password-protected documents now save their annotations (the PDFium path reopened the copy without the password). PDFium mode now reads /CA when PDFium reports no colour (any annotation with an appearance stream).
- **Pages:** rotate, delete and insert blank pages in place as incremental updates; insert pages of another document (FPDF_ImportPages); extract, arrange (reorder, repeat, rotate), split and merge into new files (FPDF_CreateNewDocument). Each page takes its inherited attributes and what it uses, copied once per source. Fonts, images and other resources identical across sources are written once. Links and outline items keep working when their page is in the result: named destinations become explicit there, so no name tree is carried. Those that lead to pages left out are dropped. Merges get one outline item per source. Form fields are kept with only the widgets on the pages taken. The structure tree, document JavaScript, the open action and signature values are not carried.
- **Save as copy:** incremental (the current revision as it is) or a full rewrite that drops unreachable objects and keeps the document's encryption.

### Performance
Off-screen rendering (thumbnails, printing, export, cold open) was about twice PDFium's time. A profile of the corpus (`vectorpdf perf`: build, analysis, fonts, images, replay by command, Direct2D flush, readback) showed where: images decoded up to three times per render and converted pixel by pixel (CalRGB JPEGs, sRGB ICC images, CCITT fax), every glyph of every run tessellated again by Direct2D's outline text rendering, antialiased rectangular clips composited through GPU intermediates (a table with a clip per cell), and a page buffer of megabytes on the managed heap per render (a full garbage collection every few renders). What changed:
- **Text** comes from a device-wide glyph atlas for body sizes (≤ 64 device pixels, plain fill): each glyph rasterized once per size and quarter-pixel position by exact area, baselines on whole pixels as PDFium places glyphs, runs drawn as sprite batches. Larger, stroked, clipping and translucent text keeps Direct2D's outline rendering; printing keeps glyph runs as text.
- **Rectangular clips** take every pixel they touch, unantialiased (PDFium's outer pixel rectangle).
- **Reuse**: a display list's analysis, each image's decode outcome (the pixels the analysis decoded go to the paint), glyph run resolution, one recoloured brush per replayer, tile surfaces across page sizes; page pixels in native memory, as PDFium's are.
- **Core** (also used by the Skia backend): exact table-driven CalRGB/Lab conversion, row-wise and parallel 8-bit gray/RGB/indexed images, one decode of a soft mask, table-driven CCITT runs, a lexer without per-token builders, operands made from the token lexed, decoded forms and Type 3 procedures reused per page, the installed-font scan in parallel. Inline images are keyed by content stream as well as offset (two Type 3 glyphs with an inline image at the same offset showed the same image).

  - **Forms (`PdfNativeFormService`).** `IPdfFormService` on the engine: one model per widget in `/Annots` order with full names, kinds (push button, check box and radio told apart), values, options, flags and the widget's check state; values set with appearances regenerated (`PdfFormFiller`) as one incremental update (a damaged file is rewritten whole first); field rules and calculations in `/CO` order as `PdfFormScripts` recognises them (no JavaScript is executed; custom scripts still get the "filled as typed" notice); reset to `/DV`; XFDF (nested names, as Acrobat writes it) and FDF export and import, told apart by content, unknown and read-only fields skipped and reported; flatten draws every visible widget into its page (generated appearance where the form asks for one, else its own for its state), removes the fields and writes the file whole. The viewer's Fill Form Fields dialog fills the open revision in memory (it used to write a PDFium copy), and Tools gets Import Form Data, Export Form Data, Reset Form and Flatten Form. On-page editing (`FormFieldsLayer`, `FormSession`) was already native.
  - **Signatures (`PdfNativeSignatureService`).** `IPdfSignatureService` on `PdfSignatureValidator`. Signing (`PdfSigner`) and validation in the viewer were already native; `PdfiumSignatureService` stays as the oracle in `SigningTests`. Status follows PDFium's verifier (intact over the whole file: Valid or Untrusted by chain; bytes changed: DocumentModified; not a signature: Invalid), except that a later revision the signature permits keeps it Valid/Untrusted where PDFium says DocumentModified.
  - **Redaction (`PdfNativeRedactionService`).** `IPdfRedactionService` on `PdfRedactor` (the viewer already redacted natively): pending areas per document, normalized areas mapped to the crop box, written to a new file.
  - **Document Safety (`PdfNativeSafetyInspector`).** The `PdfiumSafetyInspector` report from the engine's parse: `/JavaScript` name tree, `/EmbeddedFiles` name tree, security revision, URI and launch link actions on the first 50 pages (same limitation note). It also finds what PDFium's API does not: scripts and launch actions in the open action, document, page, field and annotation event actions, annotation actions and `/Next` chains, so its counts are never lower.
  - **Save Clean Copy (`PdfNativeSanitizer`).** Form fields are flattened into their pages (they stay visible, as in PDFium's copy), then only the pages go into a new document (no outline, form, name trees, open action, document actions, information dictionary or XMP metadata). Launch, remote (GoToR/GoToE) and unrecognised link actions, media and file attachment annotations, every `/AA`, and annotation actions are removed (new `SanitizedContentKind.TriggeredAction`); pop-up parents and reply targets of removed annotations are cut so nothing removed stays reachable. Only reachable objects are written. The copy is re-opened and inspected; a copy that is not clean is deleted. Hidden layers stay hidden (the optional-content configuration is kept).
  - **Everything else.** Compare (window and report) and Recognise Text open the documents in the engine (`VectorPdfRenderer`, `PdfVectorTextService`); Document Safety and Save Clean Copy use the native services. Organise, merge, split, extract and embedded files were already native. The `PdfiumEngine` call sites left in `MainViewModel` are all PDFium-mode branches.

## 5. Remaining work, in priority order

1. **Live host tuning, remainder:** done for deep zoom. A page-spanning path is tessellated only in a window around the requested tile: curves crossing the window are split, strokes cut, and fills closed along the window's edge, so every pixel inside is unchanged. A zoom step starts preparing the visible tiles' tessellations at once, while the previous tile stays on screen stretched. On the 400-curve fixture, the first tile at 1600 % went from 0.4–0.67 s to about 0.25 s (p50), and zoom request to crisp tile from about 0.33 s to 0.16 s. Page bitmaps still take the readback path; they are cached and reused. Geometries smaller than 1,024 device pixels are drawn directly rather than realized: building thousands of realizations (001767.pdf p2, a map of 9,381 small symbols) cost 20–80 s for the first tile at a new zoom, where drawing them costs milliseconds, and a realization of a shape that fits a tile or two is rarely drawn twice. Over the 20 heaviest GovDocs pages, the worst first tile (p95) went from 49.6 s to 1.0 s at 1600 % and from 81 s to 1.4 s at 800 %.
3. **Real-world corpus:** GovDocs1 batch 001 (284 US-government PDFs) is in the corpus (3 197 files; pages fully vector 99.64 %, area 99.90 %). The font and image gaps it exposed are closed (CFF FontMatrix normalization and glyph matrices, substitute fallback chains, CCITT/JBIG2/JPX masks, JPEGs through their colour space): GovDocs pages fully vector 97.39 % -> 99.46 %. Next: more batches, CAD and scanned books; the residual high-frequency diffs on scanned grids are resampling, not errors.
4. **Remaining font coverage:** a CFF FontMatrix that is singular is still refused (classified). (Done: a Type 1 (`FontFile`) simple font without /Widths now advances by its program's hsbw/sbw widths through its FontMatrix, as PDFium does; `Type1ProgramWidthsTests`.)
5. **Transparency remainder:** done for non-isolated groups over transparent backdrops (inside isolated groups, knockout elements and soft masks) and for blending elements of non-isolated knockout groups. Printing such pages keeps everything outside the groups' areas as vectors (see Printing). Left: JBIG2 colour extension and 12-pixel extended templates. Colour management is done (see Colour management); left there: the PDF/A output intent as the CMYK default and blending in CMYK group spaces.
5a. **PDF/A-1b flattening remainder:**
   - Flattened areas are DeviceRGB; on a CMYK document they get the sRGB default space, not CMYK pixels for its CMYK output intent.
   - Text in a transparent Type 3 font keeps only its advance (Type 3 glyphs ignore the rendering mode), so it is not searchable.
   - Still refused: form field widgets that are translucent or whose appearance draws transparency, translucent annotations without an appearance stream (the converter generates theirs afterwards), and translucent annotations with NoZoom or NoRotate. Over the whole veraPDF and Isartor corpus (2 906 files), these are the 13 PDF/A-1b refusals left; 165 files are flattened, and none fails with an error.
   - The copy over the images repeats marked-content operators, so MCIDs appear twice on flattened pages (no matter for PDF/A-1b; it would for PDF/A-1a or PDF/UA).
   - (M9) Pages are no longer drawn by PDFium when flattening, so its buffer limit on very large pages at 600 dpi no longer applies.
6. **Real-world corpus:** the rights-cleared corpus is conformance-heavy; add scanned, CAD and publishing samples under their licences.
7. **Forms and signatures remainder:** opt-in online revocation checks when validating; the ESIC extension entry; timestamp requests with hashes other than SHA-256.
7a. **Encryption remainder:** certificates on smart cards/HSMs that need a PIN prompt are untested (the Windows CNG provider shows its own prompt); re-encrypting a saved copy for the same certificate recipients (password encryption is done).
8. **Release remainder:** the app and installer are Authenticode-signed with a self-signed certificate, locally and in GitHub releases (`.github/workflows/release.yml`, eng/signing/README.md). A certificate from a trusted CA is future scope. Startup, installer-size and PDFium-free gates are in place (eng/releasegate). PDFium-free gate, test coverage: the PDFium-free test job runs 586 viewer test cases (it was 364 of 594); the developer build runs 713, the 127 more being the PDFium row of each engine theory and the PDFium-only tests.
